# CounterCraft 项目现状与接续计划

核对日期：2026-10-10。依据代码、提交记录、MODLOG、私有实验报告和截图。
本文描述已证实的范围；原计划中的轮数不是当前完工预测。

## 项目要做什么

最终目标是在 CS2 本机离线场景中使用真实 Minecraft Java 模拟，能够建造、
挖矿、合成，继续扩展到生物和红石，并让两边的画面、玩家和碰撞规则一致。

目前采用双进程：隔离的 Minecraft 1.20.1 Fabric 客户端负责原版世界模拟，
CS2 的 ReShade/D3D11 插件接收画面和深度。桥接走 localhost；Minecraft 的
原版逻辑仍在 Minecraft 中运行。用户现有 PCL/OptiFine 实例和存档不参与开发。

## 已做到什么程度

| 工作线 | 当前结果 | 证据边界 |
| --- | --- | --- |
| 完整 MC 画面和连续输入 | 已有可操作的离线 alpha，F8 切换 | 实际 CS2 中验证了移动、转向、创造库存取物、挖掘、放置和基础聊天 |
| 原版玩法 | 放置、挖掘、2×2 合成、拉弓；红石灯、生物受伤、生存伤害和复活有记录 | 部分只在 MC 客体接口验证，不能都算 CS2 原生操作验收 |
| 会话和启动 | 配置启动器、隔离 MC 所有权、Steam `-insecure`、安装前备份和退出恢复 | 多轮实际会话有 Restored 记录；部分 CS2 退出使用精确 PID 终止 |
| 输入生命周期 | 暂停/恢复、断连、epoch 更新、MC 窗口调整和比例适配 | 整体世界切换、完整控制清单和长期稳定性尚未验收 |
| 帧传输 | 有界 CPU 拷贝、异步 GPU 读回、20 FPS 限流 | 尚非 GPU 共享，不能承诺 60 FPS |
| 世界融合实验 | 宿主相机读回、世界深度快照、当前 GPU 相机一致性检查和保留遮挡 | 已出现可提交合成的帧及 MC 场景内容；真实墙体遮挡未通过正式验收 |
| 跨游戏模拟 | 仍未完成 | CS2 玩家与 MC 玩家、碰撞、区块、实体和武器语义没有联动 |

可操作的 alpha 与完整世界融合是两条不同的工作线。默认启动仍是完整 MC
画面；实验融合需要显式 `-WorldFusion`，不能与玩法输入同时启用。

## 最近实验到底进到哪里

已提交的 `1674db5` 阶段解决“后续深度清空抹掉武器遮挡”的问题，当时后续
深度资源切换仍导致拒绝，文档因此记载可提交合成的帧数为零。

工作区还有 7 个未提交文件，实际包含后续跨资源保护、资源/绘制/复制跟踪及
诊断视图。私有第 8 次资源实验报告记录：

- 世界边界 238,022 次，GPU 相机/深度配对 238,021 次。
- 可提交合成 127,198 次，匹配客体渲染相机的帧 12,017 次。
- `invalid` 为 7,176，最后错误是 `Unsupported host pose for Minecraft camera relay`。
- 128 槽的资源事件跟踪发生截断；该报告的 `finalReport` 为 false，是会话中保存的快照。
- `liveOcclusionVerified` 为 false；截图出现 MC 内容，但没有受控墙前/墙后对照。

进一步读取第 9 次资源会话的 ReShade 日志，找到 `finalReport=true` 的最终记录：
世界边界和 GPU 配对均为 1,795,916，可提交合成为 145,144，匹配客体相机帧
为 23,908；重连累计 896 次、`invalid` 为 2,988，最后边界拒绝为 1，
事件跟踪仍截断，实景遮挡验证仍为 false。重连频繁也是后续稳定性工作的重点。
上述不同会话的计数不能相加作为性能指标，也没有证明每个“可提交”帧都通过
GPU 相机门或绘制了 MC 像素。

因此不能继续沿用“融合管线始终为零”的旧判断，也不能宣称完整融合已完成。
相机的不支持姿态、跟踪截断、菜单/HUD 保护及可重复场景验收仍需要检查。
最后一次资源会话的恢复记录为 Restored；本次接续开始时未发现运行中的
CS2 或 Java 游戏进程。

## 代码分工

| 位置 | 职责 |
| --- | --- |
| `minecraft/src/main` | Fabric 钩子、原版动作/输入、相机控制、帧和深度读回 |
| `bridge` | 协议、坐标转换、健康检查、玩法验证和离线分析工具 |
| `cs2/native/src/receiver.cpp` | localhost 接收、客体相机验证、输入/文字队列与过期处理 |
| `cs2/native/src/world_fusion.cpp` | 宿主深度/相机边界、资源事件处理、覆盖保留和效果绑定 |
| `cs2/native/src/coverage_journal.hpp` | 单个世界快照之后的有界资源写入历史和覆盖前保留 |
| `cs2/native/src/depth_coverage.cpp` | GPU 遮挡保护掩码；清空/复制不会擦除已识别像素 |
| `cs2/reshade` | 相机一致性检查、深度比较、最终显示和实验诊断视图 |
| `game`、`scripts` | 构建、受监督启动、加载器安装/恢复、测试和打包 |

## 本次继续完成的工作

接续现有跨资源实验，并补齐几处可能漏掉遮挡的事件：

1. 复制目标即使从未绑定为深度视图，也会按公开资源描述注册并保留待检查状态。
2. 在清空或复制覆盖前采样原内容；复制后取消旧的“已清空”基线。
3. 在效果阶段检查所有待处理目标，包括最终未绑定的纹理；成功之后才允许
   相机/深度配对，GPU 采样失败时拒绝本帧。
4. 后续不兼容深度写入、复制或清空会拒绝本帧；资源历史最多 16 项，
   每个区间最多 32 次采样，超过限制同样拒绝。
5. 补上事件重放及实际 GPU 清空/复制/覆盖测试，并更新过时进度。

跨资源深度允许 MSAA 世界范围内的 resolve 值，超出范围的值被保护；这是一种
保守策略，不是完整宿主渲染语义证明。诊断视图默认关闭：1 为相机状态
（蓝色未就绪、红色不匹配、绿色匹配），2 为覆盖掩码，3 为客体画面。

本轮没有启动真实游戏；新检查可能减少实际场景的可提交帧，需要重新实测。
检查结果：原生 CTest 20/20、Python 桥接 41/41、加载器/监督器 33/33、
客体启动器 3/3、打包保护 3/3。Java 源码没有改动，本轮未重跑 Java 构建。
ReShade 完整效果编译及新的回调路径仍需真实加载验收。

## 之后按什么顺序做

1. **重新运行受监督的融合实验。** 先核对 Steam build 与当前备份，使用新会话
   目录，重验证私有相机/通道标定。检查新增拒绝原因 6、采样次数上限和不支持
   姿态的触发条件，确认恢复记录及安装目录差异为空。
2. **固定相机，做实际墙前/墙后遮挡验收。** 在隔离 MC 世界中放置位置已知的
   方块，对照 CS2 已知墙体，记录相机、深度、掩码、相机匹配视图和最终截图。
   前方方块应可见、墙后方块应被挡住；枪械、角色、MSAA 边缘、客体天空、
   菜单和 HUD 要分别检查。通过后才改变实景验收结论。
3. **建立玩家/碰撞统一规则。** 先明确由哪边驱动位置、重力、跳跃和碰撞，
   再同步 MC 玩家与区块，避免当前只跟随渲染相机、模拟玩家留在原地的问题。
4. **把融合与玩法输入接起来。** 在同一套位置/碰撞规则下验证建造、挖矿、
   库存和合成，再扩展生存、生物和红石的 CS2 场景操作验收。
5. **稳定性与发布。** 验证宿主/客体 resize、换世界、断流和退出，归因 D3D11
   引用计数警告；测量实际开销与延迟，再考虑 GPU 共享和新 alpha 包。

第一项可继续使用 `docs/world-fusion.md` 的启动入口。标定、游戏资源、存档、
截图和日志留在忽略目录；每个阶段记录实测证据、提交相关源文件并正常推送。
